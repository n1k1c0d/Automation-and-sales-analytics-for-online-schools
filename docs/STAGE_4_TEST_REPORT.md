# Отчёт о проверке этапа 4

## Ошибки Groq и повторы · TASK-4.4.7

После исправления обработки `json_validate_failed` на Windows с PostgreSQL 16.16 прошли все 226 тестов и обе проверки Ruff. На имитации Groq проверены успех со второй попытки с сохранением расхода первой, возврат `invalid_response` после трёх последовательных HTTP 400 с этим кодом и немедленная ошибка при нарушении локальной схемы Pydantic. В тесте `evaluate_rejections()` повторно отправленная партия вошла в расчёт точности один раз. Квота Groq в этом прогоне не расходовалась.

В исходном прогоне TASK-4.4.7 от 20 ноября 2026 года на Windows прошли все 224 теста, включая 189 модульных и 35 интеграционных на PostgreSQL 16.16. Для прогона использовали флаги `--integration -q -ra -W error`. Обе проверки Ruff прошли. Транспорт Groq был имитирован. Во время итогового прогона процесс pytest разрешал TCP-подключения только к локальному компьютеру.

- Для HTTP 429, 500, 502, 503 и 504 проверены предел в три попытки, задержки и завершение с контролируемой ошибкой. Для `Retry-After` проверены восстановление, некорректное значение и слишком долгое ожидание.
- Тесты подтвердили обработку ошибок доступа, квоты, таймаута, отказа модели, обрыва по лимиту, некорректного JSON, ошибочных ссылок на комментарии и цитат. Проверены отсутствие каждого API-ключа и чтение счётчиков Groq при доступной, частичной и отсутствующей статистике.
- При имитации двух повторов оценка обработала три комментария в двух партиях. В отчёте сохранились четыре записи расхода в порядке запросов — `24, 1000, null, 1000` токенов.
- На SQL-отчёте по 500 синтетическим лидам после ответа HTTP 503 сводка вернула эталонные 500 лидов, 8 506 500,00 ₽ и конверсию в оплату 39,33 %. Вопрос по тому же отчёту вернул источник с максимальной выручкой и сумму из PostgreSQL.

## Проверка пяти CLI-команд · TASK-4.4.6

20 ноября 2026 года каждую команду запустили отдельным процессом Python в каталоге без `.env`. Процессы получили настройки `GROQ_*`. Все пять команд вернули JSON и код 0 на реальных ответах `qwen/qwen3.8-27b`. Использовались только синтетические данные.

| Команда | Проверенный результат |
|---|---|
| `scripts.check_llm` | Pydantic подтвердил `{"status":"ok"}`. Получены модель и статистика токенов. |
| `scripts.ai_sales classify` | Для комментария «Банк отказал в рассрочке.» получены `bank_declined` и цитата из комментария. |
| `scripts.ai_sales evaluate` | Запуск без аргументов дал 18 верных меток из 18 в трёх партиях. |
| `scripts.ai_sales summarize` | Все шесть значений в сводке совпали с исходным отчётом. |
| `scripts.ai_sales ask` | На вопрос о лидере по выручке возвращён `webinar` с 7 000,00 ₽. У второго источника было 2 000,00 ₽. |

Автотесты проверяют адрес Groq, схему Pydantic и фактический лимит запроса для каждой команды при удалённом `OPENAI_API_KEY`. При обрыве партии `evaluate` сохраняет JSON в stdout, пишет подсказку в stderr и возвращает код 1. Полный прогон на PostgreSQL 16.16 — 208 тестов. Обе проверки Ruff прошли.

## Реальная оценка и лимиты

Статус на 19 ноября 2026 года — ожидается `OPENAI_API_KEY` в локальной конфигурации. Пробный вызов `evaluate` завершился с кодом 2 на проверке настроек до обращения к OpenAI. Реальная точность, частота обрывов, фактическая модель и расход токенов будут зафиксированы после запуска с настроенным ключом.

Стандартная проверка использует 18 примеров в трёх тарифицируемых запросах. Для оценки влияния размера партии повторите дополнительный набор с размерами 8 и 4 при неизменных модели и лимите. Дополнительный набор требует соответственно 3 и 6 запросов. [Настройка ключа и лимитов](LLM.md#настройка)

```powershell
$results = 'data/local/stage-4'
New-Item -ItemType Directory -Force $results | Out-Null
uv run --locked python -m scripts.ai_sales evaluate |
  Set-Content -Encoding utf8 "$results/classification-smoke.json"

foreach ($batchSize in 8, 4) {
  uv run --locked python -m scripts.ai_sales evaluate data/synthetic/ai/rejection_challenge_cases.json --batch-size $batchSize |
    Set-Content -Encoding utf8 "$results/classification-batch-$batchSize.json"
}
```

Из JSON перенесите в отчёт точность, ошибки и пропуски по каждой категории, фактические модели из `batches`, лимиты из `settings` и токены из `usage_by_request`. Для оценки обрывов сравните `output_limit_batches` и `output_limit_rate_pct` при одинаковой модели. Размер партии и лимит подбираются по этим замерам.

Для проверки сводок сохраните обычный SQL-отчёт и выполните `summarize` с теми же периодами. Зафиксируйте используемый лимит, модель, статус и токены. При обрыве сравните повторный прогон с отдельным лимитом сводки. [Создание SQL-отчёта и запуск сводки](AI_ANALYSIS.md#сводки-и-вопросы-по-kpi)
