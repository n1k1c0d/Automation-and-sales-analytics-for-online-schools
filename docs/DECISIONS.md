# Журнал технических решений

## ADR-001 — Модульный монолит

- Дата принятия — 2026-11-18.
- Проблема — разместить загрузку, аналитику, API и AI в поддерживаемой архитектуре первой версии.
- Варианты — модульный монолит, микросервисы, приложение без разделения по ответственности.
- Решение — единый Python-backend с модулями для данных, API, сервисов, расчёта KPI и AI. Дашборд и n8n взаимодействуют с ним через API.
- Причина — небольшому проекту достаточно одного backend-приложения и одного места расчёта KPI.
- Последствия — нужно следить за зависимостями модулей и удерживать бизнес-правила в сервисах и аналитике. При появлении реальной потребности отдельный модуль можно выделить позже.

## ADR-002 — PostgreSQL 16 и миграции Alembic

- Дата принятия — 2026-11-18.
- Проблема — воспроизводимо хранить события, связи и точные денежные суммы.
- Варианты — PostgreSQL, SQLite, файловое хранение. Для управления схемой рассмотрены миграции Alembic и отдельные SQL-скрипты.
- Решение — PostgreSQL 16 через Docker Compose для локальной разработки, SQLAlchemy 2.x и psycopg 3 для доступа к данным, Alembic для всех изменений схемы.
- Причина — стек поддерживает внешние ключи, фиксированную точность и время с часовым поясом. Версии миграций делают изменения схемы воспроизводимыми.
- Последствия — для локального запуска понадобится Docker Compose. Тесты миграций и взаимодействия с БД выполняются в отдельной базе PostgreSQL. Версии миграций служат источником изменений схемы.

## ADR-003 — Общий расчёт KPI и ограниченная роль LLM

- Дата принятия — 2026-11-18.
- Проблема — обеспечить одинаковые показатели в API, BI и автоматических отчётах.
- Варианты — отдельные расчёты у каждого потребителя, общий аналитический слой, расчёт итогов средствами LLM.
- Решение — вычислять метрики в SQL/Python и отдавать агрегаты через API. LLM работает с обезличенным текстом и агрегатами и возвращает проверяемую структуру.
- Причина — формулы можно воспроизвести на тестовом наборе и проследить до исходных событий.
- Последствия — изменения определений проходят через справочник KPI, проверки и общий расчёт. AI-выводы требуют валидации схемы и контроля качества.

## ADR-004 — Подключение инструментов по подзадачам

- Дата принятия — 2026-11-18.
- Проблема — показать целевые границы проекта и сохранить понятный старт локальной разработки.
- Варианты — создать все конфигурации сразу или добавлять их вместе с проверяемыми функциями.
- Решение — на TASK-1.1 подготовить документацию, шаблон окружения, Python-пакеты и маркеры пустых директорий. Python-конфигурация появится на TASK-1.2, конфигурация PostgreSQL на TASK-1.3, конфигурация миграций на TASK-1.5.
- Причина — каждую конфигурацию можно проверить вместе с её первым рабочим сценарием.
- Последствия — инструкции запуска будут дополняться по мере готовности. Выбор лицензии для публикации остаётся за владельцем проекта.

## ADR-005 — Окружение Python и версии зависимостей через uv

- Дата принятия — 2026-11-18.
- Проблема — воспроизводимо создать `.venv` на Python 3.12 и установить зависимости приложения и проверок.
- Варианты — стандартные `venv` и `pip` с отдельным фиксированным списком версий, либо uv с `pyproject.toml` и `uv.lock`.
- Решение — хранить в Git `.python-version`, `pyproject.toml` и `uv.lock`. В основных зависимостях указать FastAPI и Uvicorn, инструменты проверок разместить в группе `dev`.
- Причина — одна команда создаёт окружение по проектной версии Python и устанавливает зафиксированные версии прямых и транзитивных зависимостей.
- Последствия — для локальной разработки нужен uv. Изменения зависимостей проверяем вместе с изменениями в `uv.lock`. Команды в README используют `--locked`.
- Дополнение TASK-1.6 — установка uv использует режим `copy`. При проверке чистого окружения Windows отказал в создании жёсткой ссылки на пакет из кеша, связанного с рабочей папкой OneDrive. [Настройка `link-mode`](https://docs.astral.sh/uv/reference/settings/#link-mode)

## ADR-006 — Ветки для разработки и выпусков

- Дата принятия — 2026-11-18.
- Проблема — сохранять в `master` проверенную версию сервиса во время разработки новых функций.
- Варианты — вести работу в `master` или использовать отдельную ветку разработки.
- Решение — коммиты по задачам делать в `dev`. Готовую версию переносить из `dev` в `master` после проверки.
- Причина — в `master` доступно состояние последней выпущенной версии, пока новые изменения проходят проверку в `dev`.
- Последствия — перенос изменений в `master` становится отдельным шагом выпуска.

## ADR-007 — Настройки и проверка локального PostgreSQL

- Дата принятия — 2026-11-18.
- Проблема — одинаково использовать реквизиты подключения из Docker Compose и Python и сохранять данные при пересоздании контейнера.
- Варианты — отдельные файлы настроек и каталог данных на хосте или общий `.env` и именованный том Docker.
- Решение — локальный `.env` содержит параметры базы. Docker публикует порт на loopback-адресе и хранит данные в `postgres_data`. Pydantic проверяет параметры, SQLAlchemy подключается через psycopg 3.
- Причина — именованный том продолжает хранить данные после замены контейнера. Проверка SQL из Python подтверждает доступ через те же параметры, которыми будет пользоваться приложение.
- Последствия — начальные реквизиты применяются при инициализации пустого тома. Команда проверки соединения используется отдельно от HTTP-проверки приложения.

## ADR-008 — Ограничения и индексы первой схемы

- Дата принятия — 2026-11-18.
- Проблема — обеспечить целостность воронки и подготовить таблицы к отчётам по периоду и по лиду.
- Варианты — хранить статусы через PostgreSQL ENUM, отдельные справочники или `TEXT` с проверками. Для связанных записей рассмотрены каскадное удаление и запрет удаления родителя при наличии ссылок.
- Решение — использовать `TEXT NOT NULL` с именованными `CHECK` для статусов и дат, обязательные внешние ключи с `RESTRICT`, `TIMESTAMPTZ` для событий и `NUMERIC(12, 2)` для оплат. Добавить индексы по датам и индексировать внешние ключи ведущими столбцами составных индексов.
- Причина — схема сохраняет связанные события продаж и даёт явно проверяемые правила для первой миграции. Составные индексы соответствуют поиску событий лида во временном диапазоне.
- Последствия — изменение списка статусов проводится миграцией. Результативность первоначальных индексов проверяется вместе с аналитическими запросами. История переносов, статусов и возвратов требует отдельных данных.

## ADR-009 — Миграции и метаданные SQLAlchemy

- Дата принятия — 2026-11-18.
- Проблема — воспроизводимо создать схему PostgreSQL и проверять изменения перед применением.
- Варианты — запускать DDL при старте приложения или применять отдельные версии схемы через Alembic.
- Решение — хранить неизменяемые ревизии Alembic. `env.py` загружает общую `Base.metadata` и использует настройки подключения приложения. Режим `--sql` работает автономно через диалект PostgreSQL.
- Причина — журналы ревизий и SQL позволяют видеть, какие изменения будут применены. Откат проверяется в отдельной базе.
- Последствия — новые изменения схемы добавляются отдельными ревизиями. Сравнение Alembic дополняется проверками самих ограничений PostgreSQL на тестовых записях.

## ADR-010 — Транзакции сервиса и изоляция интеграционных тестов

- Дата принятия — 2026-11-18.
- Проблема — в одном сценарии можно записывать несколько связанных сущностей. Интеграционным тестам нужна реальная схема и отдельное место для записи данных.
- Варианты — фиксировать каждую операцию внутри сервиса или управлять транзакцией в вызывающем коде. Для тестов рассмотрены постоянная база и временная база на запуск.
- Решение — сервис принимает `Session` и получает UUID через `flush()`. Вызывающий код фиксирует транзакцию. Флаг `--integration` запускает тесты в отдельной временной базе со схемой из Alembic.
- Причина — несколько операций можно откатить вместе. Уникальное имя базы позволяет повторять и запускать проверки параллельно.
- Последствия — интеграционный запуск использует роль PostgreSQL с правом создания базы. Модульные тесты работают автономно.

## ADR-011 — Идентификаторы для повторного импорта

- Дата принятия — 2026-11-18.
- Проблема — при повторной загрузке CSV или Excel одна внешняя заявка или оплата должна сохранить уже присвоенный внутренний UUID.
- Варианты — пара `source_system` и `external_id` в импортируемой таблице либо отдельная таблица соответствий с поддержкой нескольких внешних ключей на один объект.
- Решение — в первой версии использовать уникальную пару в каждой импортируемой таблице. Обе части обязательны для импорта, внутренние записи могут иметь два `NULL`. PostgreSQL разрешает конкурирующие вставки через уникальное ограничение. Импорт помечает повтор или конфликт с существующей записью и сохраняет её данные.
- Причина — одна пара описывает один внешний ключ каждой записи, а внутренние UUID остаются связями между таблицами. Такой объём достаточен для повторных загрузок из одного источника. [Уникальные ограничения и конфликты в PostgreSQL](https://www.postgresql.org/docs/16/sql-insert.html#SQL-ON-CONFLICT)
- Последствия — колонки и импортёр реализованы на TASK-2.2. Для идемпотентности файл содержит стабильные текстовые ID. Если понадобится связать несколько систем с одним внутренним объектом, таблицу соответствий можно добавить отдельной миграцией.

## ADR-012 — Воспроизводимые синтетические данные

- Дата принятия — 2026-11-18.
- Проблема — подготовить проверяемый набор связанных событий продаж для разработки импорта и KPI.
- Варианты — генерировать неповторяемые записи текущей датой или использовать фиксированные параметры и сохранять результаты в CSV.
- Решение — генерировать CSV из фиксированного начального дня и `seed`. Внешняя пара и имя таблицы определяют UUID. Каждый новый набор публикуется целиком. Уже существующий набор с теми же данными принимается при повторном запуске.
- Причина — по тем же параметрам можно повторить тесты и сопоставить каждую строку до и после импорта. Повторные уроки, заявки и оплаты дают сценарии для проверки KPI.
- Последствия — файлы из папки вывода воспроизводятся командой и игнорируются Git. Изменение даты или объёма для уже сгенерированной папки требует другого пути, если меняется её содержимое.

## ADR-013 — Формат файлов и транзакция импорта

- Дата принятия — 2026-11-18.
- Проблема — принимать данные из CSV и Excel, сохраняя идентичность записей и показывая, какая строка требует исправления.
- Варианты — откатывать весь импорт при первой ошибке строки либо сохранять корректную часть. Для Excel рассмотрены чтение книги целиком и чтение листов через `openpyxl` в режиме `read_only`.
- Решение — проверять структуру набора перед записью. Обрабатывать таблицы в порядке зависимостей. Использовать одну транзакцию и точки сохранения для вставок. Уникальные пары из ADR-011 добавлены миграцией `0002`. PostgreSQL присваивает внутренние UUID, а родительские записи определяются по внешним ID. Excel читается через `openpyxl` без вычисления формул. Для ячеек даты Excel часовой пояс задаётся явно, а строки ISO 8601 несут собственное смещение. [Режим чтения openpyxl](https://openpyxl.readthedocs.io/en/stable/optimized.html)
- Причина — порядок обработки сохраняет ссылки, уникальность защищает от повторов и конкурирующих вставок. Понятный отчёт позволяет исправить отдельные строки.
- Последствия — код `1` означает частичный успех. После исправления строк тот же файл можно передать повторно. Внутренние записи существующей базы сохраняют предыдущий UUID и могут иметь пустую внешнюю пару.

## ADR-014 — Единый расчёт отчёта по продажам

- Дата принятия — 2026-11-18.
- Проблема — получить одинаковые KPI в общем отчёте, динамике и срезах при повторных уроках, заявках и платежах.
- Варианты — отдельные запросы для каждого представления или общий набор строк событий с группировкой по нескольким измерениям.
- Решение — один параметризованный SQL-запрос с `UNION ALL` по видам событий и `GROUPING SETS` для итогов и разбивок. Когорта учитывает первый проведённый урок за всю историю лида и использует `EXISTS` для исходов. Денежные значения и проценты остаются десятичными. [Агрегаты PostgreSQL](https://www.postgresql.org/docs/16/functions-aggregate.html)
- Причина — каждая запись участвует в своём показателе. Повторный платёж увеличивает сумму, а лид входит в число платящих один раз за период.
- Последствия — периоды с нулевой активностью содержат все дни. Сравнение выполняется в одном снимке БД по явно указанным датам. Потребители отчёта используют один контракт.

## ADR-015 — Контролируемое обновление данных CRM

- Дата принятия — 2026-11-18. Реализация запланирована перед включением синхронизации изменяемых полей из CRM.
- Проблема — повторная выгрузка CRM может содержать новый статус лида, исправленную сумму либо более старую версию уже загруженной записи.
- Решение — выделить для CRM отдельный режим обновления по паре `(source_system, external_id)`. Для каждой сущности явно определить разрешённые поля и переходы статусов. Внешние ключи сохраняются. Исправления времени событий и денежных сумм требуют отдельных правил.
- Порядок применения — хранить версию или время обновления из CRM. Применять более свежие изменения, считать повтор той же версии с теми же данными дубликатом, а разные данные одной версии регистрировать как конфликт. Устаревшие версии пропускать с объяснением в отчёте.
- Аудит — в одной транзакции записывать изменение и журнал с внешним ключом, версией, временем импорта и значениями разрешённых полей до и после изменения.
- Текущее поведение импорта CSV и Excel следует ADR-013. Изменившаяся строка с тем же внешним ключом получает статус `conflict`, сохранённые поля сохраняют исходные значения.

## ADR-016 — HTTP-контракт импорта и KPI

- Дата принятия — 2026-11-18.
- Решение — версионировать маршруты префиксом `/api/v1`. Импорт принимает CSV или Excel в форме `multipart/form-data` и использует общий сервис записи. KPI принимает типизированные query-параметры и использует тот же отчёт, что и CLI. [Файлы в FastAPI](https://fastapi.tiangolo.com/tutorial/request-files/), [модели query-параметров](https://fastapi.tiangolo.com/tutorial/query-param-models/)
- Результат обработки — импорт возвращает HTTP 200 с отчётом, когда транзакция завершилась, включая частичный успех. Неверный формат или структура запроса возвращает HTTP 422. При сбое PostgreSQL API возвращает HTTP 503 с общим описанием.
- Ограничения — 366 дней на период отчёта, 5 МиБ на тело запроса и 50 МиБ на содержимое Excel после распаковки. [Контракт и примеры](API.md)

## ADR-017 — Структурированные ответы LLM

- В TASK-4.4 провайдер и политика повторов заменены на GroqCloud с Qwen и максимумом в три попытки. Приведённое ниже решение описывает исходную версию. [Действующий контракт](LLM.md)
- Дата принятия — 2026-11-19.
- Решение — использовать OpenAI Responses API с моделью `gpt-5-mini` по умолчанию. Pydantic-модель определяет JSON Schema запроса и повторно проверяет ответ перед передачей в аналитику. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- Обработка ошибок — классифицировать ошибки транспорта, HTTP и генерации. Одна попытка на вызов позволяет вызывающему коду решать, когда повторять запрос.
- Учёт расходов — ограничивать входные символы и выходные токены, возвращать сведения об использовании и рассчитывать оценку по явно заданным тарифам. [Настройки клиента](LLM.md)

## ADR-018 — Выводы AI со ссылками на KPI

- Дата принятия — 2026-11-19.
- Решение — модель выбирает ссылки на агрегаты и проверки гипотез. Значения, разницы периодов и порядок срезов определяет Python по исходному отчёту.
- Классификация — одна основная причина на комментарий, цитата для проверки классификации и отметка `unclear` при недостатке сведений. Эталонные метки применяются локально при оценке качества. [Сценарии и тестовый набор](AI_ANALYSIS.md)
