# Журнал технических решений

## ADR-001 — Модульный монолит

- Дата принятия — 2026-11-18.
- Проблема — разместить загрузку, аналитику, API и AI в поддерживаемой архитектуре первой версии.
- Варианты — модульный монолит, микросервисы, приложение без разделения по ответственности.
- Решение — единый Python-backend с модулями для данных, API, сервисов, расчёта KPI и AI. Дашборд и n8n взаимодействуют с ним через API.
- Причина — небольшому проекту достаточно одного backend-приложения и одного места расчёта KPI.
- Последствия — нужно следить за зависимостями модулей и удерживать бизнес-правила в сервисах и аналитике. При появлении реальной потребности отдельный модуль можно выделить позже.

## ADR-002 — PostgreSQL 16 и миграции Alembic

- Дата принятия — 2026-11-18.
- Проблема — воспроизводимо хранить события, связи и точные денежные суммы.
- Варианты — PostgreSQL, SQLite, файловое хранение. Для управления схемой рассмотрены миграции Alembic и отдельные SQL-скрипты.
- Решение — PostgreSQL 16 через Docker Compose для локальной разработки, SQLAlchemy 2.x и psycopg 3 для доступа к данным, Alembic для всех изменений схемы.
- Причина — стек поддерживает внешние ключи, фиксированную точность и время с часовым поясом. Версии миграций делают изменения схемы воспроизводимыми.
- Последствия — для локального запуска понадобится Docker Compose. Тесты миграций и взаимодействия с БД выполняются в отдельной базе PostgreSQL. Версии миграций служат источником изменений схемы.

## ADR-003 — Общий расчёт KPI и ограниченная роль LLM

- Дата принятия — 2026-11-18.
- Проблема — обеспечить одинаковые показатели в API, BI и автоматических отчётах.
- Варианты — отдельные расчёты у каждого потребителя, общий аналитический слой, расчёт итогов средствами LLM.
- Решение — вычислять метрики в SQL/Python и отдавать агрегаты через API. LLM работает с обезличенным текстом и агрегатами и возвращает проверяемую структуру.
- Причина — формулы можно воспроизвести на тестовом наборе и проследить до исходных событий.
- Последствия — изменения определений проходят через справочник KPI, проверки и общий расчёт. AI-выводы требуют валидации схемы и контроля качества.

## ADR-004 — Подключение инструментов по подзадачам

- Дата принятия — 2026-11-18.
- Проблема — показать целевые границы проекта и сохранить понятный старт локальной разработки.
- Варианты — создать все конфигурации сразу или добавлять их вместе с проверяемыми функциями.
- Решение — на TASK-1.1 подготовить документацию, шаблон окружения, Python-пакеты и маркеры пустых директорий. Python-конфигурация появится на TASK-1.2, конфигурация PostgreSQL на TASK-1.3, конфигурация миграций на TASK-1.5.
- Причина — каждую конфигурацию можно проверить вместе с её первым рабочим сценарием.
- Последствия — инструкции запуска будут дополняться по мере готовности. Выбор лицензии для публикации остаётся за владельцем проекта.
