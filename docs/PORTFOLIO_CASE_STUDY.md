# EduFlow AI · от выгрузки CRM до отчёта о продажах

Руководителю продаж онлайн-школы нужно ответить на два разных вопроса. Сколько денег поступило за лето? Какая доля клиентов после первого урока в итоге оплатила обучение? В выгрузке один клиент может фигурировать несколько раз из-за перенесённого урока, повторной банковской заявки или оплаты частями. Один общий подсчёт строк дал бы неверный ответ на оба вопроса.

## Что разработано

Локальный MVP принимает выгрузки CSV и Excel, связывает пять типов записей, строит SQL-отчёт и показывает его в Streamlit. Руководитель может выбрать менеджера или канал, спросить о сумме оплат и получить ежедневный отчёт в Telegram. Для аналитика есть CLI и REST API, результаты которого можно независимо сверить с SQL. [Архитектурная схема](ARCHITECTURE.md) · [Демонстрация](DEMO_SCENARIO.md)

## Как устроен расчёт

**PostgreSQL, SQLAlchemy и Alembic.** Связи, допустимые статусы и суммы проверяются на уровне БД. Сервис импорта разрешает внешние ID в порядке зависимостей. Ограничение уникальности для пары `source_system` и `external_id` отличает повторную строку от новой записи. Изменение существующей строки видно оператору как конфликт. Миграции позволяют повторить эту схему в отдельной базе. [Модель данных](DATA_MODEL.md) · [Правила импорта](DATA_IMPORT.md)

**FastAPI и Streamlit.** Один параметризованный SQL-запрос собирает события и отдельно считает исходы когорты первого проведённого урока. Так повторные уроки, заявки и частичные платежи сохраняют свой смысл на каждом уровне агрегации. На стандартном наборе получилось 105 уникальных оплативших за лето и 118 оплативших к октябрьскому срезу из 300 клиентов с первым уроком летом. API и CLI читают один расчёт. Streamlit отвечает за фильтры, сравнение периодов и представление. [SQL отчёта](../sql/queries/sales_report.sql) · [Формулы KPI](KPI_DEFINITIONS.md)

## Где пришлось ограничить генеративную модель

Классификатор Qwen периодически получал от Groq `HTTP 400 json_validate_failed` даже на двух комментариях. Уменьшение партии само по себе не решило проблему. Для генерации используется компактная схема. После двух отказов провайдера при генерации строгого JSON классификатору доступна одна попытка в режиме JSON Object. В обоих режимах Pydantic и предметные проверки проверяют состав ответа, количество записей и соответствие каждого ID исходному комментарию. В статистике остаются режим, попытки и только известное потребление токенов. [Контракт и ошибки клиента](LLM.md)

У определённой причины отказа есть проверяемая цитата. Для короткого комментария приложение сохраняет весь исходный текст, для длинного требует дословную подстроку до 160 символов. При неясной причине сохраняется `null`. Если руководитель спрашивает о самом доходном канале, модель выбирает показатель и разбивку, а максимум ищет Python среди строк SQL-отчёта. Ноль сохраняет значение нуля. При отсутствии значений по выбранным показателям сервис возвращает `insufficient_data`. [Сценарии и ограничения AI](AI_ANALYSIS.md)

## Что значит «отчёт доставлен»

n8n формирует сообщение из проверенных KPI. Ошибка HTTP при чтении отчёта и потеря ответа Telegram после отправки требуют разных действий. Для первого случая допустим ограниченный повтор. Во втором сообщение могло уже дойти. Relay резервирует отправку в SQLite и сверяет ответ Telegram с ожидаемым чатом и идентификатором сообщения. Для подтверждённой доставки повторное выполнение находит квитанцию. При неопределённом исходе доставка получает статус `unknown` и требует ручной сверки. Это позволяет повторно открыть исполнение и объяснить, что именно произошло. [Проверки Telegram и n8n](STAGE_5_TEST_REPORT.md)

## Практическая ценность и следующий шаг

Аналитик может повторно загрузить выгрузку, увидеть расхождения по строкам и дать руководителю ссылку на один воспроизводимый расчёт. Для утренней сводки уже есть расписание, формат сообщения и журнал доставки. Экономию времени и влияние на продажи можно измерить после внедрения в школе.

Демо рассчитано на одну локальную установку и синтетические либо специально подготовленные обезличенные данные. Перед работой с реальной CRM потребуются авторизация, правила обновления изменившихся записей, псевдонимизация и проверка качества модели на реальных формулировках. [Дорожная карта](ROADMAP.md)
